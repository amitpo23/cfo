# תכנית המשך: השלמה, בדיקות ופריסה של רצף

7 בספטמבר 2026. הצעת ספרינטים לעורך הפעיל; אינה שינוי סטטוס ואינה אישור לפרוד. סטטוס ביצוע מתעדכן רק ב-[MASTER_EXECUTION_PLAN.md](MASTER_EXECUTION_PLAN.md).

## נקודת המוצא שאומתה

- [דוח העורך](audits/2026-09-06-provider-business-expansion.md) מתעד גבייה עם פיצולים, יתרות וביטולי הקצאה, ותשלום ספק יחיד בשקלים עם בקשה מאושרת והתאמות בנק חלקיות. יש ממשקי ווב ומושקו משותפים.
- [ראיות הבדיקה](audits/evidence/2026-09-06-provider-final-validation.json): 2,763 בדיקות בסוויטה, תשעה שערים מקומיים, 39 בדיקות ממוקדות לאחר השער, בדיקות דפדפן עם API מדומה ותרגילי PostgreSQL סינתטיים. בדיקת Neon דולגה.
- בבדיקת המחקר הנוכחית 56 קבצים תואמים ל-SHA256 שנשמר בראיות. זו התאמת קבצים, לא הרצת בדיקות מחדש ולא כיסוי לכל קובץ ב-worktree. יש שינויים staged וגם unstaged.
- [מטריצת התהליכים](provider_business_evidence.json): 41 שורות — 7 ממומשות מקומית, 28 חלקיות, 3 לא נבדקו, 1 חסומה בספק, 1 דורשת הגדרת בעלים, 1 מוחרגת. אין להסיק מכך אחוז כיסוי מוצר.
- היעד שנבדק מקומית הוא migration `95eb3062ca48` ו-71 טבלאות. לפני פריסה יש לחשב את היעד מחדש מהמועמד ולבדוק את מקור הפרוד בפועל; הערכים ההיסטוריים ב-Gate 0 אינם מצב חי.

**המלצה:** ספרינט ראשון שמסיים מועמד פריסה מוגדר למסלולים הקיימים. ספרינטים נוספים משלימים תשלומים מתקדמים, התאמות ומשרד. מוכנות לפריסת מסלול מוגבל אינה שוויון מלא מול המתחרים.

## סדר הבדיקות לכל מועמד שחרור

1. במהלך פיתוח: TDD לפי הריפו ובדיקות ממוקדות למקרה עסקי, במיוחד replay, כשל חלקי, הרשאות, שינוי מקור ו-concurrency. אין שתי ריצות pytest במקביל.
2. דפדפן: מסלולי collection/payable הקיימים, שולחן עבודה ומובייל RTL, עם הצלחה, pending, חריג, ביטול מקומי ומעבר בין ארגונים.
3. הוסף מסע HTTP עם backend מקומי ו-DB סינתטי לאותם תרחישים; בדיקת דפדפן שמיירטת את כל ה-API אינה לבדה הוכחת חיבור לשרת. אם כבר קיים מסע כזה במועמד, הרחב אותו.
4. PostgreSQL: migration מבסיס עם נתונים וממסד ריק, שימור החלטות קיימות, מגבלות DB, restore סינתטי ובדיקות ההתנגשות ב-tests/postgres_offline. אין DSN חיצוני או נתוני לקוח בבדיקות אלו.
5. לאחר השינוי האחרון במועמד: `python scripts/qa_gate.py` ללא `--env-file` וללא דילוג frontend, בסביבת Python 3.12 של הריפו. השער כבר כולל סוויטת pytest, בדיקות tenancy, build/lint/typecheck, route audit ו-drift; אין להפעיל לצדו או מיד לפניו סוויטה מלאה כפולה ללא סיבה.
6. אם מתקנים אחרי השער: בדיקות ממוקדות לתיקון, ואז אימות המועמד המעודכן לפי היקף השינוי ולפי חובת הסוויטה לפני commit. אין לשייך תוצאת 2,763 של גרסה קודמת לכל שינוי עתידי.
7. `git diff --check` ו-`git diff --cached --check`, סקירת כל קובצי המועמד לרבות CI ומיגרציות, תיעוד commit וקישור לראיות. שמור manifest גם לקבצים שאינם ברשימת 56 החתימות הישנה.

2,763 הוא בסיס מדווח, לא יעד לכמות בדיקות. ירידה במספר דורשת הסבר, תוספת בדיקות אינה הוכחת כיסוי, ו-skip משמעותי חייב להיות גלוי. אין צורך לתקן באופן גורף עשרות אלפי אזהרות תאריך במסגרת הספרינט.

## מסלול פריסה מדורג

### הכנה מקומית עד נקודת אישור

המפתח מכין commit בענף העבודה המתאים לאחר הבדיקות, רשימת קבצים ממוקדת ותוכן PR לסקירה. יש לשמר שינויים שאינם שלו; אין `git add .` גורף, push או commit ל-main. אם נדרש פרסום PR דרך push, הפעולה נשארת למורשה או לאישור מפורש בהתאם להוראות הריפו.

חבילת השחרור תכלול:

- commit מוגדר והיכולות הכלולות/החסומות.
- revision יעד, שרשרת שדרוג, תאימות הקוד הישן והחדש וסיכון לחלון ביניהם.
- תכנית גיבוי ושחזור פרוד, אחראי וראיות נדרשות; תרגיל סינתטי אינו גיבוי פרוד.
- הגדרות וסודות נדרשים לפי שמות בלבד, בלי ערכים; flags ושערי כתיבה.
- בדיקות preview/פרוד שאינן מפעילות ספקים בתשלום; בדיקות ספק מתוארות בנפרד.
- מדדי עצירה: drift, שגיאת הרשאות/דליפת ארגון, כפל בקשה/תשלום, פער יתרות לא מוסבר או חריגת תקציב.
- תכנית חזרה: השבתת הפיצ'ר/עבודות הרקע הרלוונטיות באופן מורשה, rollback קוד רק אם תואם לסכימה, ושחזור נתונים לפי תכנית מתואמת כשנדרש. downgrade שמוחק החלטות אינו rollback בטוח. פעולה כספית שכבר בוצעה אינה מתבטלת עם קוד.

### אחרי אישור השחרור הספציפי

המפעיל המורשה מבצע את התהליך ב-[GATE0_DEPLOYMENT_RUNBOOK.md](GATE0_DEPLOYMENT_RUNBOOK.md): PR מאושר, גיבוי/נקודת שחזור מאומתים, חלון מאושר, SUPER_ADMIN, פריסה ומיגרציה בסדר תואם למועמד. מעדכנים מראש את יעדי ה-revision בנוהל השחרור; אין להשתמש במספרי אוגוסט כאילו הם היעד הנוכחי.

ממשיכים רק עם revision היעד, drift ריק ב-PostgreSQL, שימור נתונים ורשומת GLOBAL_SCHEMA_MIGRATION. אין stamp head על תיקון חלקי. preview אינו מורשה להתחבר אוטומטית ל-DB של פרוד או להפעיל cron וספקים.

אחרי בדיקות פריסה בסיסיות פותחים את היכולות המאושרות לתיק פיילוט אחד. יכולות כספיות שלא הוכחו נשארות חסומות. אישור deploy אינו אישור לתשלום, שידור, הודעת לקוח או סגירת מנה; כל אחת נשארת כפופה למסלול האישור שלה.

### הוכחת SUMIT והפיילוט

המפעיל מאמת את מוצר הספק, ההרשאות, החשבון, ה-consent, זהות המוטב והתקציב. לחבילת ספרים: הצעה מאושרת → ניסיון מתועד פעם אחת → בדיקת הפורטל לפי SOP → צירוף ראיה לתיק/מנה/תקופה → התאמה למאזן הרשמי → סגירה נפרדת אם אושרה. אין להבטיח endpoint readback שאינו מתועד.

שומרים את שערי הפיילוט ב-MASTER: 20 מסמכים, ראיות רישום רשמי, שבעה מחזורי בוקר וחבילת תקופה באימות משולש. הרחבה חודשית כפופה לראיות לפחות 25 ימים ירוקים. אלה תנאי יציאה מהפיילוט; אין לדרוש שבעה ימים שכבר עברו כתנאי לפריסה הראשונה או לסמן אותם כגמורים בהרצת טסטים.

לכל משימה כתוב במקור הסטטוס היחיד את התוצר, תנאי הקבלה, התלות והראיות. השלם פיתוח מקומי ובדיקות מבלי להמתין לאישור על פעולות שכבר מותרות. חסימת ספק אינה סיבה לעצור משימות מקומיות בלתי-תלויות. אל תעקוף אישורי בעלים, הוראות פרוד או מכסות. הכן מראש את חבילת ה-PR והפריסה; כשהיא מוכנה, פרט בדיוק איזה אישור חיצוני נדרש ועבור איזה commit, סכימה והפעלה. בקשת תכנון הספרינט אינה כשלעצמה אישור פריסה חיה.

בסיום הצג: מה אפשר לעשות במערכת כעת, אילו תרחישים הוכחו, אילו בדיקות רצו על המועמד, מה נכלל בשחרור, מה נשאר חסום ואיזו ראיה/החלטה תסיר כל חסימה. המשך ל-S2 ול-S3 לפי סדר התלויות והיקף העבודה המאושר, בלי להשאיר משימה כללית בשם ״תשלומים מתקדמים״.
