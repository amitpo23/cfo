# פרומפט המשך לעורך הקוד — השלמות לפי מחקר מתחרים

להעתיק את הטקסט הבא לעורך שעובד על רצף. זהו פרומפט לביצוע עתידי, לא הוראה שבוצעה במסגרת המחקר.

---

המשך את העבודה הקיימת ברצף. המטרה היא לסגור את פערי המוצר שאותרו מול FinBot, DOKKA ויומנאי, ולהביא מסלול מלא של מסמך → פקודה מאושרת → ספרים → תשלום/התאמה → סגירת תקופה → CFO.

קרא תחילה את AGENTS.md ו-CLAUDE.md, את docs/REZEF_OPERATING_SYSTEM.md, docs/rezef_capabilities.json, docs/MASTER_EXECUTION_PLAN.md, ואת docs/COMPETITOR_CAPABILITY_RESEARCH_2026-09-06.md. לפני עבודה חשבונאית טען את מרכז הידע שאליו מפנה docs/bookkeeper_kb/README.md. לפני יכולת ספק אמת מול מרכז הידע והמפרט שלו. המחקר מגדיר כיווני מוצר; הוא אינו תחליף למפרט API או למקור דין.

בדוק git status ואת השינויים הפעילים. עבודת CollectionWorkbench, collection_allocation_service, provider_event_service והרחבת Open Finance כבר בתהליך. אל תדרוס אותה ואל תממש תחליף. קרא את התוצאה הסופית שלה לפני קביעה מה עדיין חסר. אין לבטל שינוי של עורך אחר או להריץ סוויטת pytest במקביל אליו.

בנה מפת דלתא לפי C01–C36 שבמחקר: מצב בפועל, קוד קיים, התוספת, תלויות, סיכון, בדיקת קבלה וראיית סיום. הפרד בין שינוי מקומי, אינטגרציה שלא הוכחה, יכולת שלא תועדה אצל הספק, ופער שתלוי בהטמעה/אישור. אל תשנה סטטוס במפת היכולות ללא ראיות. שמור סטטוס ביצוע רק ב-MASTER_EXECUTION_PLAN, בהתאם לשער הפעיל; תכניות המשך הן backlog ולא הוכחת השלמה.

בצע את ההשלמות המקומיות הנדרשות לפי התלויות, תחילה A ו-B במחקר. אל תעצור בהצעת תכנית אם ניתן להשלים את המימוש המורשה. הרחבות שוק ב-C ו-D שאינן מקדמות את השער הפעיל יישארו מפורקות ומוכנות להמשך בהתאם לחוזה הפרויקט.

1. **קליטה וראיות:** תקן את מסלול המייל שאוסף רק application ושומר את הצרופה הראשונה. כל צרופה רלוונטית מקבלת יחידת טיפול, מקור וסטטוס. תמוך ב-image MIME; בדוק כפילות בין ערוצים. הוסף פיצול/מיזוג מבוקר עם מפת עמודים ושימור קובץ המקור. סכום שלא חולץ אינו אפס עסקי. כשל במסמך אחד אינו מעלים את האחרים.
2. **מסך מסמך ופקודה:** הרחב את המסכים הקיימים להצגת מקור לצד שדות ושורות פקודה, חשבונות, מסים, ראיות, רמת ביטחון וחריגים. השתמש במסווג ובכללי המס הקיימים. הבדל בין מסמך מקור, הצעת פקודה, אישור מקצועי, בקשת ביצוע וראיה שהספרים קלטו אותה. הוסף בעל טיפול והיסטוריה.
3. **גבייה והתאמות:** שלב את המימוש החדש, ואז סגור רק פערים שנותרו. כסה יתרות חלקיות, מניעת הקצאת יתר, עבודה חוזרת, מקור משתנה ותנועות זמניות. הבדל בין ביטול הקצאה, ביטול מסמך והחזר כסף. הרחב ל-AP לפי חוזה ראיות ברור. מטבעות שונים/עמלות/החזרים אינם התאמה אוטומטית על בסיס סכום דומה.
4. **דוחות וסגירת תקופה:** העבר תבניות, תזמונים והיסטוריית הרצות של report_builder_service מזיכרון לאחסון עמיד ומבודד ארגון. בנה checklist וניירות עבודה עם מקור ליתרות ותלויות. snapshot יומי אינו סגירת ספרים. SUMIT createbatch נשאר בלתי-מאומת עד הראיה החיצונית הנתמכת; אין להמציא readback או close endpoint.
5. **עומק AP:** הרחב את מדיניות האישורים הקיימת לסבבים עסקיים, תורים, האצלה ותזכורות. שמור הפרדה מסמכות חתימה. הוסף שיחה ותיוג בתוך מסמך. לבניית התאמה משולשת נדרשות שורות הזמנה וקבלת סחורה אמיתיות, תשלוחים חלקיים וחריגי מחיר/כמות; document_type לבדו אינו מימוש.
6. **יבוא, למידה ויצוא:** עטוף את יבוא החשבונות והפקודות הקיים באשף הצטרפות עם מיפוי, בדיקות סכומים, תקופות וחזרות. הוסף יבוא מבנה אחיד לפי מפרט מאומת. למד מתוך היסטוריה מאושרת ורק בתוך התיק. openfrmt מסומן DRAFT: אל תסיר זאת לפני אימות. לכל תוכנת יעד וגרסה בנה מתאם נפרד והוכחת קליטה; CSV גנרי אינו ארבע אינטגרציות.
7. **עומק חשבונאי:** פרק סטורנו, נעילת תקופות, הוצאות מראש, הפרשות, פקודות מחזוריות, רכוש קבוע והפרשי שער לחבילות נפרדות עם דוגמאות מאושרות. שמור מקור, גרסה וסיבת שינוי. אל תייצר מקור דין מכלל שנלמד מתיקונים. איחוד חברות מחייב קבוצת בעלות, מיפוי וביטולים; לוח משרד אינו דוח מאוחד.
8. **מוצר ואיכות:** חבר את ניהול המשרד הקיים לחוסרים, בעלי משימות ומסלול לקוח קצר. מדוד זמן אדם להשלמת מסמך, דיוק שדות/פקודה, שגיאות שקטות ועלות. תרגום, תמיכה, תמחור והסמכות יתועדו גם כתלויות עסקיות; אין להציגן כגמורות בגלל שנוסף מסך.

השתמש במודלים ובשירותים הקיימים ככל האפשר. כל יחידה חדשה חייבת organization_id, מקור/זהות יציבה, בדיקת הרשאות, ראיות ו-idempotency במקום המתאים. אל תפתח מסלול API עוקף תקציב או מנגנון אישורים מתחרה. הימנע משכתוב גורף או מהחלפת SUMIT כמערכת הספרים הרשמית ללא החלטה ארכיטקטונית נפרדת.

פעל לפי TDD של הריפו: טסט נכשל למקרה העסקי לפני המימוש, ואז בדיקות ממוקדות. לממשק כספי בדוק מסע משתמש אופליין בעברית RTL ובמובייל, כולל חריגים והרשאות. לפני commit נדרשת הסוויטה הרשמית הירוקה, בתיאום כך שלא ירוצו שתי ריצות במקביל. בדיקות מול ספקים ופרוד אינן חלק מסוויטת האופליין.

אין קריאות חיות, תשלום, החזר, שידור, סגירה, שליחת הודעות ללקוחות, שינוי סכימת פרוד, push או deploy מכוח הפרומפט הזה. שמור את אישורי הבעלים, שערי העלות ותהליך ה-PR הקיימים. כשהשלמה תלויה בהם, השלם קודם קוד, דוגמת בקשה, בדיקות ותכנית אימות ניתנים לסקירה; סמן במדויק מה נשאר חיצוני. היעדר endpoint מתועד הוא גבול ספק, לא היתר להמציא אחד.

בכל סיום חבילה מסור: מה עובד מקצה לקצה, קבצי המימוש, הבדיקות שבוצעו ותוצאותיהן, אילו סעיפי C נסגרו ובאיזה היקף, ומה נשאר מגודר. אין לסיים ב״כל יכולות המתחרים קיימות״ ללא מטריצת ראיות, ואין להציג בדיקת mock כהוכחת התנהגות חיה.
